# jSS7: первый сквозной стенд проверки КИЕ

Модуль запускает два отдельных Java-процесса с RestComm jSS7
`org.restcomm.protocols.ss7.map:map-load:8.0.0-179`. Между ними проходит
настоящий обмен MAP USSD через TCAP/SCCP/M3UA/SCTP на loopback.
TCP-подмены и синтетического CSV вместо протокольного обмена нет.

Это первый этап: проверка реализуемости подписанного отчёта и независимого
сопоставления счётчиков. OsmoSTP, распределённая топология, действующие ML-модели,
периодические окна под нагрузкой и проверка операторской эффективности
в этот этап не входят. Для адаптера используются штатные клиент и сервер
нагрузочного примера jSS7; узкий доступ к их закрытым методам закреплён версией
зависимости и проверяется сборкой и запуском.

## Схема наблюдений

1. Клиент выполняет заданное число завершённых MAP-диалогов.
2. Сервер записывает идентификаторы реально полученных запросов.
3. Отдельный Python-агент читает только локальный журнал сервера и по HTTP
   возвращает КИЕ: идентификатор узла, идентификатор запуска, nonce запроса,
   счётчик принятых диалогов и HMAC-SHA256.
4. Независимый наблюдатель читает PCAP, выделяет TCAP Begin и End и удаляет
   повторные идентификаторы. Для короткого запуска используется одна новая
   SCTP-ассоциация; повторное использование TCAP ID в ней не предполагается.
5. Детектор проверяет подлинность и свежесть КИЕ и сопоставляет счётчик с PCAP.
   Он не получает название сценария, метку, ограничитель отчёта или журнал узла.
6. Только оценщик сопоставляет решение с меткой сценария.

КИЕ передаётся отдельным HTTP-каналом после завершения трафика. Это не расширение
MAP и не полная реализация протокола КИЕ из диссертации. Ключ создаётся для
каждого вызова runner, хранится во временной папке и не включается в артефакты.
Сохранённый MAC нельзя перепроверить после удаления ключа; результат его проверки
фиксируется успешным прохождением runner. Для долгосрочной публичной проверки
подлинности потребуется отдельный дизайн с асимметричной подписью.

## Сценарии и модель нарушителя

| Сценарий | Реальные диалоги | Подписанный отчёт | Ожидаемый результат |
|---|---:|---:|---|
| normal | 20 | фактический счётчик | нет тревоги |
| legitimate_surge | 40 | фактический счётчик | нет тревоги |
| matched_honest | 30 | фактический счётчик | нет тревоги |
| concealed_activity | 30 | не более 20 | расхождение 10, тревога |

В последнем сценарии узел действительно обслуживает дополнительные запросы,
а агент скрывает часть выполненной активности, сохраняя корректный MAC.
Предполагается, что нарушитель контролирует отчёт и ключ ведомого узла, но не
наблюдатель и его PCAP. Подпись сама по себе не делает счётчик правдивым.
Это контролируемая инжекция неисправности/фальсификации, а не эксплуатация
уязвимости jSS7. Все процессы находятся на одном хосте; изоляция от атакующего
с правами root здесь не проверяется.

Каждый сценарий создаёт новые процессы и отдельную трассу. Порог расхождения
равен нулю и применим только к полностью завершённому, без потерь захвата окну.
Для асинхронных рабочих окон потребуются согласование границ и калибровка шума.

## Запуск в Linux

Нужны Java 8, Maven, Python 3.10+, `libsctp1`, `lksctp-tools`, `tcpdump`, `tshark`.
Для tcpdump нужны root или возможность `sudo -n tcpdump`.
Запускать из корня репозитория:

```bash
python3 -m unittest discover -s tests -p test_jss7_kie.py -v
mvn -B -ntp -f experiments/jss7_kie/pom.xml package
python3 -m experiments.jss7_kie.run_lab --out runs/jss7-kie-first --repetitions 2
```

Каталог `--out` должен быть новым. Порты 2345 и 3434/SCTP, 18080/TCP должны
быть свободны. Runner завершает только созданные им процессы. Windows годится
для компиляции и тестов обработки отчётов; настоящий SCTP-прогон выполняется
в Linux, включая WSL с подходящим ядром.

## GitHub Actions

Workflow `.github/workflows/jss7-kie-lab.yml` работает на `ubuntu-24.04`,
запускается вручную либо при изменении файлов модуля в push/PR. Выполняет два
повторения четырёх сценариев. Отсутствие SCTP, ошибка сборки, неполный обмен,
потери захвата, неверный MAC или ошибка ожидаемого обнаружения не считаются
успешной проверкой. Артефакты сохраняются и при сбое после начала эксперимента.

На обычном runner можно проверять функциональную корректность. Результаты
задержек и пропускной способности нельзя переносить на операторскую сеть:
клиент, сервер и монитор разделяют ресурсы одной виртуальной машины.

## Результаты

`summary.json` содержит статус `passed`, `failed` либо `invalid`, фактические
TP/FP/TN/FN и результаты сценариев. Метрики считаются по запускам; это малая
детерминированная проверка работоспособности, не статистическая оценка FPR/Recall.
`provenance.json` сохраняет Git-версию, состояние рабочей папки, версии окружения
и SHA-256 библиотек. Каждый сценарий сохраняет PCAP, журналы, извлечённые TCAP ID,
подписанный отчёт и решение. Журнал узла включён для диагностики, но не читается
наблюдателем.

### Выполненная локальная проверка

27 октября 2026 года: Maven-сборка успешна, полный набор из 42 Python-тестов
репозитория прошёл. В Ubuntu под WSL с Java 8 выполнены два повторения всех
четырёх сценариев: 240 завершённых MAP-диалогов, TP=2, FN=0, FP=0, TN=6.
В обоих сценариях сокрытия наблюдатель получил 30 диалогов, подписанный отчёт —
20; расхождение составило 10. Легитимное увеличение нагрузки тревогу не вызвало.
Все восемь отчётов прошли проверку MAC.

Локальные доказательства сохранены в `runs/jss7-kie-local-03/`: итог в
`summary.json`, окружение и хеши в `provenance.json`, трассы и журналы в папках
сценариев. Эти файлы исключены из Git общим правилом для `runs/`.
Проверка GitHub Actions ещё не выполнялась; локальный прогон использовал root
для захвата пакетов, а workflow использует `sudo -n` на GitHub runner.
Полученные восемь результатов подтверждают работоспособность стенда,
но недостаточны для вывода об эффективности метода в реальной сети.

## Следующий этап

Подключить транзитный OsmoSTP; перенести наблюдателя на независимый узел; добавить
периодические запросы КИЕ с неполными окнами, потери/повторы, таймауты и
восстановление; затем подключить извлечение признаков существующего детектора.
Для оценки переноса с имитационной модели заранее зафиксировать модель и пороги,
а стендовые метки использовать только для итоговой оценки.

# V10 — единая многосценарная модель с контролируемой компрометацией NF

**Отдельная версия от ветки `experiment/current-v9`.** Это новый V10, а не
восстановление закрытой экспериментальной ветки старого V10. V9 и `main`
не изменяются. V10 проектируется как отдельный воспроизводимый эксперимент
с новой **моделью `TG_V10`** и расширенным **генератором атак**.

## Что моделируется

- **S1:** изменение регистрационного профиля NRF/NSSF.
- **S2:** запрос обнаружения запрещённого политикой типа NF (UDM).
- **S3:** подмена маршрута исследовательского потребителя.
- **S4:** повышенная нагрузка с ошибочными запросами.
- **S5:** согласованная малозаметная нагрузка трёх NF в одной зоне.
- **S6, S7, S8, S9:** структурная нагрузка 2, 3, 4 или 5 NF в одной
  восьмиузловой зоне; исходный принцип ступенчатой волны и код функций
  `v6_count/v7_count/v8_count/v9_count` не меняются.
- **C:** изменение фактической конфигурации исследовательской NF.
- **F:** подмена доставляемого отчёта независимого контроля.
- **R:** повтор старого отчёта.
- **D:** недоставка отчёта.
- **G:** быстрый, медленный, прерывистый и разрешённый рост нагрузки.
- **S10 (новое):** имитация последствий компрометации отдельной **программной
  исследовательской NF slot-4**, а не удалённый взлом ОС или штатной NSSF.

На новом 3600-оконном расписании **все** исходные 40 эпизодов прежнего
`attack_schedule` (36 S1–S4/C/D/F/G/R + 4 S5) сохраняются. Добавлены
16 структурных эпизодов S6–S9 (по четыре размера группы для каждого)
и **три S10-эпизода** по 30 окон. Всего **59** эпизодов на seed; интервалы
не перекрываются, состав групп определяется seed до теста.

### S10: граница доверия и три режима

| Вариант S10 | Что *фактически* меняется на стенде | Независимое наблюдение |
|---|---|---|
| `node_config` | В конфигурационном файле работающего изолированного исследовательского NF-процесса записано изменённое состояние | Отдельный наблюдатель подписывает фактическую контрольную сумму; легитимная ожидаемая конфигурация не меняется |
| `node_report_tamper` | То же изменение NF **плюс** изменение доставляемого локального отчёта *после* его подписания | Подделка не проходит HMAC; доверенный подписывающий процесс и ключ остаются внешними по отношению к атаке |
| `node_sbi_abuse` | Изменение NF плюс программные SBI-запросы обнаружения запрещённого по политике типа UDM | Независимый SBI-коллектор фиксирует реальный HTTP-трафик и контролируемую конфигурацию |

В `node_config` и `node_report_tamper` интенсивность SBI может
оставаться обычной. Это намеренно проверяет ситуацию, когда
**по одному трафику нельзя диагностировать захват узла**.

Контролируемая запись файла и модификация локального конверта отчёта
эмулируют *возможности* злоумышленника и последствия компрометации.
Они **не** доказывают получение привилегий, выполнение произвольного
кода, компрометацию ядра, штатной NSSF, доверенного внешнего монитора,
HMAC-ключа, RAN/UE/PDU или реального 5G-оператора. В частности, при
подмене **также доверенного** внешнего подписанного отчёта с захватом
ключа модель может получить правдоподобное «normal» — эта граница
подтверждается отрицательным программным тестом.

## Две независимые составляющие V10

1. **`TG_V10` — детектор по измеренным NF-признакам.**
   Из отдельно зафиксированной модели V9 он получает исходные
   `TG_V9` решения без переобучения. С ними объединяются
   *фиксированные до новых тестов* сигналы нарушения политики профиля,
   запрета операции, несоответствия маршрута, отчёта, проверки
   аутентичности, а также совместный порог ошибки (не менее 24
   запросов **и** доля ошибок не меньше 25%). Это эвристические
   правила, их FPR **не доказан** заранее.
2. **`V10_SECURE` — отдельный слой подтверждения на slot-4.**
   В момент принятия решения использует уже существующий
   независимый `Control.observe()` и его подписанные свидетельства.
   Ошибка подписи или достоверное расхождение конфигурации формирует
   `security_alarm`. Недоставка/несвежесть формируют
   `availability_unknown`, **не считаются обнаруженной атакой**.
   Для 31 других NF эта стратегия применяет только `TG_V10`,
   поскольку контроль конфигурации slot-4 нельзя выдавать за
   аттестацию всех 32 NF.

Результаты `TG_V8`, `TG_V9` и `TG_V10` измеряются для каждого NF в
`test/online_predictions.csv`. Отдельные решения независимого контроля
сохраняются в `test/v10_secure_decisions.jsonl`. Для объединённой
стратегии `V10_SECURE` аудитор заменяет **только** решение slot-4 на
комбинированное; никаких меток S10 или сценария для принятия решения
не используется. Метрики безопасности и состояния UNKNOWN выводятся отдельно.

## Как воспроизвести

Входной замороженный V9 из успешного S9-эксперимента 91201:
[Actions 44799761008](https://github.com/verge88/signal_network_sim/actions/runs/44799761008),
checkpoint SHA-256
`9b9776170c3798ca6c37fa3b2cd54f68e979291691625b29be03e6a214cc7fdc`.
Никаких новых весов и калибровки V9 для V10 не выполняется.

Получив исходные `frozen/model.joblib` и `frozen/manifest.json`:

```bash
python -m experiments.distributed_5g.v10_model \
  --source-v9 baseline/frozen --out experiment/frozen
```

Скопировав фиксированные `extensions.json`, `accumulation.json`,
`refinement.json` и `zone_models.json` из старого frozen-артефакта,
запустить на исследовательском Open5GS NRF:

```bash
bash experiments/distributed_5g/namespace_smoke.sh \
  --seed 91401 --out experiment/test --frozen experiment/frozen \
  --zone-models experiment/zone_models.json \
  --v10-compromise-experiment --include-if-context \
  --confirm-if-context --ml-method TG_V10 \
  --ml-confirmation-mode direct \
  --accumulator-multiplier 1.50 --recover-normal
```

Независимый аудит с восстановлением решения **по одному окну**, проверкой
криптографического отчёта, полного расписания и раздельных метрик:

```bash
python -m experiments.distributed_5g.v10_audit \
  --root experiment --frozen experiment/frozen --out experiment/audit
```

Граница между созданием программы и подтверждением научных метрик
явная: **рабочая реализация ≠ пройденная независимая проверка**.
Проверка новых полноты, FPR, per-scenario и S10 обязательно
проводится отдельно; результаты никогда не подменяются метриками
V9 на прежнем S9. Для тестов используется
`experiments/distributed_5g/test_v10_compromise.py` и отдельный CI workflow.

Основные файлы: `v10_design.py` (генерация),
`v10_model.py` (новая модель и внешний контроль),
`v10_audit.py` (честный аудит),
`experiments/accumulation_5g/collect.py` (физическая подача
HTTP-событий Open5GS и контролируемые изменения research NF).
